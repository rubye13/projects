# Рекомендации на главной: документация

Дипломный проект SkillFactory DSPR, **Рубинштейн Андрей**

Интернет-магазину нужно поднять оборот от допродаж. На главной странице три места под товары. Сервис по id пользователя возвращает три товара, которые стоит там показать. Модель - CatBoost, который ранжирует товары из недавней истории человека. Кому показать нечего, тот видит самые покупаемые товары

Качество: **Precision@3 = 4.60% на тестовой неделе** против 1.85% у популярного. В рекомендации попадает 7.9% покупок тестовой недели, у исходного бейзлайна (топ-3 до 1 июля) было 0.61%

## Задача и метрики

- **Задача**: рекомендации на главной, три товара для каждого посетителя
- **Бизнес-метрика**: оборот от допродаж, цель клиента +20%. По логу её честно не измерить, её покажет A/B-тест
- **Техническая метрика**: Precision@3, доля купленных товаров среди трёх показанных. Покупки берутся за 7 дней после момента рекомендации. Считается по всем покупателям этой недели. Если персонально показать нечего или своих товаров меньше трёх, места добиваются популярным, как в сервисе
- Дополнительно смотрю **покрытие покупок**: какая доля всех покупок недели попала в показанные товары. Это продолжение бейзлайна Марии

| `item_properties_part1.csv`, `item_properties_part2.csv` | 20 275 902 | `timestamp` int64 (мс, снимки по воскресеньям), `itemid` int64, `property` str, `value` str |
| `category_tree.csv` | 1 669 | `categoryid` int64, `parentid` float64 (пусто у 25 корней) |

Что важно про данные:

- период 3 мая - 18 сентября 2015, 1.4 млн посетителей, 235 тысяч товаров в событиях
- просмотров 2.66 млн, корзин 69 тысяч, покупок 22 тысячи, покупает меньше 1% посетителей
- из 1104 свойств читаются только `categoryid` и `available`, остальные захешированы вместе со значениями. `790` - число с префиксом `n`, похоже на цену
- 71% посетителей сделали одно действие. История за 8 недель есть примерно у каждого пятого покупателя, так что холодный старт - главная сложность

## Трансформации: из сырых файлов в датасет для обучения

Код лежит в пакете [`recsys/`](recsys/), им пользуются ноутбуки, скрипт сборки и сервис

- `events.csv`: убираю 460 полных дублей, время из миллисекунд перевожу в datetime, режу сессии по паузе больше 30 минут ([`recsys/data.py`](recsys/data.py))
- Свойства: из 20 млн строк оставляю `categoryid`, `available` и `790` (цена), значение перевожу в число. Свойства меняются во времени, поэтому на срез беру последнее значение строго до среза
- Дерево категорий: для каждой категории корень и глубина
- Срезы по пятницам. На каждый срез беру события за 56 дней до него и считаю факторы товара, пользователя и пары пользователь-товар ([`recsys/features.py`](recsys/features.py))
- Кандидаты: все товары, с которыми человек взаимодействовал за эти 56 дней. На обучении берутся люди, которые зашли на сайт в неделю после среза
- Таргеты по неделе после среза: `target` - купил товар, `target_cart` - положил в корзину или купил
- У каждого человека оставляю 50 самых свежих товаров. У ботов в истории тысячи товаров, а показываем всё равно три
- Срезы склеиваю в train, valid и test

Утечку проверял так: один и тот же срез считал на полном логе и на логе, обрезанном по срезу, факторы совпали

## Валидация

Разбиение по времени. Модель знает только прошлое и рекомендует на следующую неделю, как в жизни. Случайное разбиение не подходит: популярность товара, посчитанная по всему логу, уже знает будущие покупки

| Выборка | Срезы (пятница) | История для факторов | Таргет | Пар (до / после ограничения 50) | Покупателей недели |
|---|---|---|---|---|---|
| train | 07.08, 14.08, 21.08, 28.08 | 56 дней до среза | 7 дней после | 144 870 / 91 161 | 475-623 на срез |
| valid | 04.09 | 56 дней | 7 дней | 35 744 / 22 475 | 602 |
| test | 11.09 | 56 дней | 7 дней | 35 121 / 21 053 | 486 |

- Недели таргета не пересекаются: таргет последнего обучающего среза кончается там, где начинается valid
- Параметры подбираю на valid, тест считаю один раз в конце
- Потолок метрики: даже если идеально выбрать купленное из истории, P@3 будет 3.82% на valid и 5.42% на тесте. Остальные покупают то, чего раньше не смотрели
- Одно попадание в тесте весит 0.07 п.п., так что разница в пару десятых процента - шум

## Эксперименты

Все эксперименты - в ноутбуке [`experiments_rubinshtein.ipynb`](experiments_rubinshtein.ipynb), полная таблица - в [`reports/experiments.csv`](reports/experiments.csv)

Лучший вариант каждого семейства, Precision@3 по всем покупателям недели:

| Модель | Гиперпараметры | P@3 valid | P@3 test | P@3 test у покупателей с историей | Покрытие покупок test |
|---|---|---|---|---|---|
| Популярное | топ по покупкам за 56 дней | 1.44% | 1.85% | 3.49% | 3.19% |
| ALS (implicit) | factors=64, alpha=10, regularization=0.01, 15 итераций, веса просмотр/корзина/покупка = 1/3/5, пользователи и товары с 2+ взаимодействиями | 2.10% | 1.85% | 3.49% | 3.19% |
| LightFM | loss=warp, no_components=64, learning_rate=0.05, 60 эпох | 2.66% | 3.98% | 13.33% | 6.85% |
| Эвристика "корзина, потом свежесть" | товары из истории: сначала те, что были в корзине, потом по давности | 3.21% | 4.32% | 14.92% | 7.44% |
| Item-based по совместным просмотрам | косинус по общим сессиям, топ-30 соседей, сессии до 50 товаров, полураспад веса 7 дней, свои товары с весом 5 | 3.32% | 4.46% | 15.56% | 7.67% |
| **CatBoost** | target_cart, depth=4, learning_rate=0.03, iterations=590, до 50 кандидатов на человека | **3.54%** | **4.60%** | **16.19%** | **7.91%** |

ALS на тесте совпал с популярным до сотых. Я проверил: у обоих по 11 попаданий среди покупателей с историей, но у разных людей, общих только четыре. Популярную тройку ALS никому целиком не рекомендует, так что это совпадение, а не ошибка

Что ещё проверял (всё на valid):

- **CatBoost**: таргет `target` против `target_cart` и глубина 4 / 6 / 8, число деревьев ранней остановкой по AUC на valid. P@3 от 3.38 до 3.54%, разница в пару попаданий. Лучший `target_cart` на глубине 4. AUC у разных таргетов не сравниваю, метки разные
- **ALS**: factors 32 / 64, alpha 1 / 10. Лучше всего 64 фактора и alpha=10
- **Совет ментора убрать малоактивных** (меньше 5 взаимодействий) для ALS: матрица сжимается до 5.9 тысячи человек, в неё попадает только 31% покупателей с историей, P@3 падает с 2.05 до 1.50%. Почти все посетители тут разовые. Порог 2 качество не портит и уменьшает матрицу в 6 раз, его и оставил
- **Item-based только по новым товарам**, без истории человека: 1.33%, ниже популярного
- **LightFM**: 30 эпох - 2.49%, 60 эпох - 2.66%
- **Факторы из генератора Серёги**: топ-20 свойств товаров и доли событий по частям суток. В LightFM как признаки товара роняют P@3 до 1.77%. В CatBoost (время суток, свойства как категории) дают 3.45-3.51% против 3.51% без них, по трём сидам шум. В итоговой модели их нет
- **Кандидаты из похожих товаров**: добивать пустые места похожими по совместным просмотрам вместо популярного. Разницы нет: одно попадание в плюс на valid, одно в минус на тесте
- **Ограничение 50 товаров на человека**: 3.51% с ограничением и без, а пар на треть меньше

## Итоговая модель

- `CatBoostClassifier(iterations=590, learning_rate=0.03, depth=4, random_seed=42)`, категориальные `i_category`, `i_root`
- Учится предсказывать, что человек положит товар в корзину или купит его за неделю. Товары из истории человека сортируются по этой вероятности, берутся три лучших
- Сильнее всего на решение влияют (PredictionValuesChange, [`reports/feature_importance.csv`](reports/feature_importance.csv)): наличие товара `i_available` (29%), давность последнего контакта человека с товаром `ui_days_since_last` (6.7%), корзина этого товара у человека `ui_carts` (4.8%), был ли товар в последней сессии `ui_in_last_session` (4.5%) и конверсия товара в корзину `i_cart_rate` (4.5%)
- Для сервиса модель переобучена на всех шести срезах с теми же параметрами. Кандидаты посчитаны на конец лога, 18.09.2015 03:00: 573 765 пользователей с историей, 807 164 пары
- Запасной список для холодных: самые покупаемые товары за 56 дней до конца лога, 461686, 213834, 119736 и далее

## Сервис: как поднять Docker-образ

Образ `recsys-main:1.0` собран под `linux/amd64` и выгружен командой `docker save`. Архив лежит в релизе репозитория: [скачать recsys-main_1.0_amd64.tar.gz](https://github.com/rubye13/projects/releases/download/final-project-2-year-v1.0/recsys-main_1.0_amd64.tar.gz) (358 МБ, [страница релиза](https://github.com/rubye13/projects/releases/tag/final-project-2-year-v1.0))

```
recsys-main_1.0_amd64.tar.gz   358 МБ
sha256 12ba82117ee24343d35587f0f236bc011b3ff7133713f43690cc75d85fe00b8b
```

Нужен только Docker, данные и Python не нужны: модель и кандидаты лежат внутри образа

```bash
# загрузить образ из архива
docker load -i recsys-main_1.0_amd64.tar.gz

# запустить сервис на порту 8000
docker run -d --name recsys -p 8000:8000 recsys-main:1.0

# проверить, что поднялся (готов через 2-3 секунды)
curl http://localhost:8000/health

# рекомендации для пользователя
curl "http://localhost:8000/recommend?user_id=172"

# логи и остановка
docker logs recsys
docker stop recsys && docker rm recsys
```

GET-запросы можно открыть прямо в браузере, например http://localhost:8000/recommend?user_id=172 и http://localhost:8000/metrics

Порт можно поменять: `docker run -p 9000:8000 ...` отдаёт сервис на 9000. На Mac с Apple Silicon образ тоже запускается, Docker эмулирует amd64 и пишет предупреждение про платформу, на работу это не влияет

Проверить сервис целиком можно скриптами из папки `service/`. Им нужен только Python 3 без библиотек:

```bash
python service/smoke_test.py --url http://localhost:8000     # 27 проверок, включая кривые запросы
python service/load_test.py --url http://localhost:8000 --requests 3000 --threads 8
```

Обстрел на моём маке (образ amd64 под эмуляцией): 3000 запросов в 8 потоков, на трёх прогонах 395-455 запросов в секунду, p50 15-17 мс, p95 33-40 мс, все ответы 200. Контейнер занимает около 600 МБ памяти

## Как устроен сервис

```
запрос ─> gunicorn (1 процесс, 4 потока) ─> Flask (service/app.py)
             │
             ├─ проверка параметров, ошибки 400/404/405/413 в JSON
             ├─ Recommender (service/recommender.py)
             │     ├─ candidates.parquet в памяти: 807 тыс. пар с 37 факторами, отсортированы по visitorid
             │     ├─ ranker.cbm: CatBoost ставит вероятность каждому товару человека
             │     └─ популярное из meta.json добивает список до k
             └─ счётчики запросов, времени ответа и источников выдачи -> GET /metrics
```

- При старте сервис читает три файла из `/app/models`: `ranker.cbm` (модель), `candidates.parquet` (кандидаты с факторами), `meta.json` (параметры, дата среза, популярное). Загрузка занимает меньше секунды
- На запрос сервис бинарным поиском находит строки пользователя и прогоняет их через CatBoost. Товары сортируются по вероятности, берутся k лучших. Если своих товаров меньше k, список добивается популярным без повторов
- Пользователь без истории за последние 8 недель, как и неизвестный id, получает популярное. Для сервиса это не ошибка: новый посетитель - нормальная ситуация для главной
- Внутри контейнера сервис работает от непривилегированного пользователя, у Docker есть `HEALTHCHECK` на `/health`
- Переменные окружения: `MODEL_DIR` (где лежат артефакты, по умолчанию `/app/models`), `PORT` (по умолчанию 8000)

```json
 "max_k": 10}
```

### GET /recommend

Подборка для одного пользователя

| Параметр | Обязательный | Тип | Допустимые значения |
|---|---|---|---|
| `user_id` | да | целое | от 0 до 2^63-1 |
| `k` | нет, по умолчанию 3 | целое | от 1 до 10 |

```bash
curl "http://localhost:8000/recommend?user_id=172"
```
```json
{"k": 3, "user_id": 172, "items": [465522, 10034, 202268], "source": "personal", "personal_items": 3}
```

```bash
curl "http://localhost:8000/recommend?user_id=5&k=5"
```
```json
{"k": 5, "user_id": 5, "items": [461686, 213834, 119736, 248455, 334401], "source": "popular", "personal_items": 0}
```

Поля ответа:

- `items` - id товаров в порядке показа, всегда ровно `k` штук
- `source` - откуда подборка: `personal` (все товары от модели), `personal+popular` (у человека меньше k своих товаров, остальное популярное), `popular` (истории нет)
- `personal_items` - сколько товаров в подборке от модели

### POST /recommend

Подборки для списка пользователей одним запросом, до 1000 id. Тело - JSON-объект с полем `user_ids` (список) или `user_id` (одно число) и необязательным `k`. Заголовок `Content-Type: application/json` лучше передавать, но JSON разбирается и без него

```bash
curl -X POST http://localhost:8000/recommend \
     -H "Content-Type: application/json" \
     -d '{"user_ids": [172, 5], "k": 3}'
```
```json
{"k": 3, "results": [
  {"user_id": 172, "items": [465522, 10034, 202268], "source": "personal", "personal_items": 3},
  {"user_id": 5, "items": [461686, 213834, 119736], "source": "popular", "personal_items": 0}
]}
```

В Windows PowerShell `curl` - это другая команда, там удобнее так:

```powershell
Invoke-RestMethod -Method Post -Uri http://localhost:8000/recommend -ContentType "application/json" -Body '{"user_ids": [172, 5], "k": 3}'
```

### Ошибки

Сервис не падает на кривых запросах. Ошибка всегда приходит в JSON с полями `error` и `status`:

```bash
curl "http://localhost:8000/recommend?user_id=abc"
```
```json
{"error": "user_id должен быть целым числом, получено 'abc'", "status": 400}
```

| Код | Когда |
|---|---|
| 400 | нет `user_id`, `user_id` не целое, отрицательное или огромное число, `k` вне 1..10, лишние параметры, битый JSON, JSON не объект, пустой список, больше 1000 id, в списке не числа (в том числе `true`), переданы и `user_id`, и `user_ids` |
| 404 | неизвестный адрес |
| 405 | метод не поддерживается, например `DELETE /recommend` |
| 413 | тело запроса больше 1 МБ |
| 500 | внутренняя ошибка, текст без подробностей, трейсбек уходит в лог контейнера |

## Пересборка модели и образа

Нужны Python 3.12, данные RetailRocket в `data/raw/` и Docker

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt

# модель и кандидаты из сырых файлов, около минуты
python build_artifacts.py --raw data/raw --out models

# сервис локально, без Docker
python -m service.app

# образ под amd64 и выгрузка в архив
docker buildx build --platform linux/amd64 -t recsys-main:1.0 --load .
docker save recsys-main:1.0 | gzip > dist/recsys-main_1.0_amd64.tar.gz

# презентация из цифр ноутбука (reports/*.csv), нужен uv
uv run presentation/build_presentation.py
```

Скрипт `build_artifacts.py` сам печатает Precision@3 контрольной модели на valid и test, так что по выводу сразу видно, что сборка прошла правильно (0.0354 и 0.046)

LightFM нужен только для ноутбука экспериментов. Версия 1.17 с PyPI под Python 3.12 не собирается: в пакете C-код от старого Cython. Собирается из исходников так:

```bash
git clone https://github.com/lyst/lightfm.git && cd lightfm
pip install "cython==0.29.37" setuptools numpy
python setup.py cythonize
pip install .
```
